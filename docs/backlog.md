## Conventions

Each item has an ID, status, size estimate, source ADR, and notes.

- Status: `pending`, `in-progress`, `blocked`, `resolved`.
- Size: `XS` (~30 min), `S` (~1 to 2 h), `M` (~half day), `L` (~day or more).
- IDs are stable; do not renumber on removal. Use `resolved` instead of deleting.

## EncryptedStore multi-key legacy migration (2026-05-23)

A capability consolidation, not an audit fix. Runbook 7.4 candidate 4: the BL-181 authenticated legacy fallback was current-key only (L16); BL-196 adds an opt-in multi-key fallback over a new optional `IterableKeyProvider` Protocol, lifting the L16 restriction without breaking the default. Same conventions and ID discipline; `BL-1xx` range.

- `BL-196` [resolved] [S] `BL-181` shipped an authenticated legacy fallback under the current key only, so adopting a `VersionedKeyProvider` on a store sealed by a plain `KeyProvider` could only read values whose plaintext key matched the current ring version; legacy data under a rotated-away key required a re-encryption pass through the old store first (the `LIMITATIONS.md` L16 contract). Delivered: a new optional Protocol `memory.encryption.IterableKeyProvider` (`iter_key_ids(namespace) -> Iterable[str]`), implemented by the in-tree `RotatingKeyProvider`; a new opt-in kwarg `legacy_multi_key: bool = False` on `EncryptedStore.__init__` and `wrap_encrypted`. When opt-in, the legacy `_unseal` fallback tries the current key first, then iterates each historical key in the ring; AES-GCM authentication still gates every attempt (false-tag probability ``2**-128`` per key, accumulated ``N * 2**-128`` across the ring), so the fallback never returns a wrong plaintext. Construction validation: `legacy_multi_key=True` requires both `VersionedKeyProvider` and `IterableKeyProvider` (load-time `ValueError`s per ADR 0007). Default is unchanged so a KMS-backed provider that charges per call keeps its current-key-only behaviour. 11 new tests (`tests/memory/test_bl196_multi_key_legacy.py`) cover the iteration order, the construction guards, the BL-181 preservation when off, the historical-key decrypt when on, the AES-GCM "no silent wrong value" guarantee under the multi-key path, the envelope-still-preferred case, and the `wrap_encrypted` flag forwarding. Additive: every existing call site is unchanged. (ADR 0007, ADR 0011, runbook 7.4 #4)

Delivered: a new opt-in subclass `BoundedS3Store(S3Store)` (the bare `S3Store` keeps its prior design unchanged so an existing user pays no per-write overhead; the subclass is the explicit opt-in, same shape as `BoundedRedisStore` and `BoundedDynamoDBStore`) that stamps an `insertion-order` user-metadata attribute on every `PutObject`, set to `time.time_ns()` at write time. No auxiliary index is needed: every data object carries its own ordering attribute, so the rewrite-shifts-to-newest semantic is automatic (a fresh `PutObject` overwrites the previous metadata stamp). `evict_to_capacity` LISTs the namespace prefix, HEADs each object to read `insertion-order` and `expires-at`, filters expired-but-unswept items client-side (the BL-195 read-vs-listing parity in S3 form), sorts the live entries by `(insertion-order, key)` ascending (the secondary key sort is the deterministic tie-break for the migration case where multiple legacy items share `insertion-order = 0` and for the rare same-nanosecond collision on a fast host), and DELETEs the oldest `(live_count - max_keys)` objects. The cost shape mirrors the parent's `sweep_expired` (LIST + HEAD-per-object + DELETE-per-evicted). Migration: a pre-existing object written via a bare `S3Store` has no `insertion-order` attribute, treated as `insertion-order = 0` (oldest, evicts first); rewriting via `BoundedS3Store` stamps a fresh `insertion-order` and moves the key to newest (same shape as the BL-224 `seq` migration and the `LIMITATIONS.md` L17 `ver` migration contract). The single S3-specific divergence from the BL-214 / BL-224 designs is that the ordering source is wall-clock (`time.time_ns()`) rather than a server-side atomic counter: S3 has no equivalent primitive (conditional writes are recent and not universally available), so multi-writer deployments with clock skew can reorder writes across writers, consistent with the S3Store eventual-consistency contract; single-writer deployments stay strictly monotonic on any platform whose `time.time_ns()` advances per call. 23 new tests (`tests/memory/test_bl225_s3_bounded_sweeper.py`, moto-backed): Protocol satisfaction (subclass yes, bare `S3Store` no but still `SweepableStore`); oldest-first by insertion-order; the overwrite-shifts-to-newest contract; no-op at and under the cap; non-positive cap rejection (parametrized); expired-but-unswept items excluded from the live count; per-key audit emission; `TTLSweeper` integration on both age and capacity passes; `mset` preserves dict insertion order under FIFO; `write_content` carries the insertion-order; the migration contract (legacy items with no attribute evict first; rewriting restamps them); namespace prefix isolation (one namespace's eviction does not touch another); parent surface unchanged (read/write/delete/TTL/list_keys roundtrip); and the `wrap_acl` / `wrap_encrypted` forwarding (BL-156). Scope: S3 is the fifth and final adapter for the size-bound half of BL-135; the long-horizon compaction / summarisation / tiering half remains tracked under BL-135. Additive: the bare `S3Store` is unchanged; only the new subclass adds the metadata stamp and the Protocol surface. (ADR 0004, ADR 0008)

BL-207 / BL-208 class extension on the ensemble side. (ADR 0015, ADR 0018)

## Tenth code audit (ADR 0020, 2026-05-26)

A tenth in-depth audit, by area, against the same green gates, focused
on the *classes* the prior audits fixed pointwise. The just-merged
`BL-225` (`BoundedS3Store`) introduced two new boundaries: an
untrusted S3 user-metadata read trust boundary and a new sequential-
DELETE per-key fan-out. Both are re-instances of invariants prior
audits already generalised on neighbouring surfaces, but neither was
applied at the new boundary. The clear bugs were fixed additively
with regression tests in the same increment; ADR 0020 is the why.
Same conventions and ID discipline; `BL-2xx` range.

- `BL-226` [resolved] [S] `S3Store._get_live`, `S3Store._sweep_sync`, and `BoundedS3Store._collect_live_sync` parsed the S3 user-metadata strings `expires-at` and `insertion-order` via bare `float(exp) if exp is not None else None` and `int(seq_raw) if seq_raw is not None else 0`. Two distinct failure modes leaked past the documented `S3Store` / `BoundedS3Store` exception contract: (1) a non-finite float (`"nan"` / `"inf"` / `"-inf"`) sailed through `float()` and then through `is_expired(now, NaN)` whose `now > NaN` is always `False`, permanently masking the object from every expiry path (the BL-159 / BL-205 / BL-221 NaN-bypass class extended to the metadata-read trust boundary); (2) an unparseable string (e.g., `"not-a-number"`) raised `ValueError` out of the read / sweep / eviction scan, crashing the whole keyspace's operation on the first corrupted object (the BL-201 / BL-215 / BL-217 unparseable-input class extended to the same boundary). Delivered: two helpers in `memory/s3.py` -- `_safe_float(v: str | None) -> float | None` (returns None on missing / unparseable / non-finite via `math.isfinite`) and `_safe_int(v: str | None) -> int` (returns 0 on missing / unparseable, matching the BL-225 legacy-migration default so a corrupted entry falls back to "oldest, evict first" -- the most defensive eviction-order default). Both helpers applied at every metadata-read site (three call sites). The "corrupted = no-TTL / keep alive" semantic over the alternative "corrupted = expired / drop" is the cold-storage / audit-pack stance: losing data because a metadata attribute was malformed is worse than keeping a corrupted-TTL entry around; an operator can re-write the entry with valid metadata to restore expiry. 28 new tests (`tests/memory/test_bl226_bl227_audit10.py` BL-226 portion): 13 parametrized `_safe_float` cases (None / empty / unparseable / NaN / mixed-case NaN / +inf / -inf / Infinity / valid floats including 0, negative, large exponents), 9 parametrized `_safe_int` cases (None / empty / unparseable / float-string-not-an-int / NaN / inf / valid ints), 3 parent-`S3Store` cases (corrupt `expires-at` does not crash `read` or `sweep_expired`; NaN `expires-at` does not silently mask), 3 `BoundedS3Store` cases (corrupt `insertion-order` / `expires-at` do not crash `evict_to_capacity`; NaN `insertion-order` is treated as legacy seq=0). (ADR 0004, ADR 0008, ADR 0020)
- `BL-227` [resolved] [S] `BoundedS3Store.evict_to_capacity` ran the per-key `delete_object` loop inside `asyncio.to_thread` with no exception containment, so a single failing DELETE (S3 throttle, transient access drift, network blip) propagated out of the thread and the audit-emit loop below was never reached -- partial state mutation (the keys already deleted) with no audit emitted at all, the exact BL-202 / BL-167 audit-vs-raise parity violation generalised to the new BL-225 sequential-DELETE fan-out. Separately, the *first* failure cancelled every later delete in the batch, so a transient error on one key took out the whole eviction cycle -- the BL-222 / BL-223 per-item failure containment invariant not applied to the new fan-out. The fix contains per-key failures (catches `Exception`, lets `BaseException` propagate per the BL-165 / BL-223 invariant), collects the actually-deleted keys inside the thread, and emits audit only for those after the thread returns; the function returns the count of *actual* deletions, not the count of *attempted* ones, so `TTLSweeper.evicted_total` is truthful. A failed key remains alive and the next `TTLSweeper` cycle retries it (the BL-199 sweeper-resilience contract already applied to the age-only sweep path). 4 new tests (`tests/memory/test_bl226_bl227_audit10.py` BL-227 portion): partial-failure audits only successes (one key deletes, one throws, audit emits exactly once for the success and zero for the failure; state mutation matches the audit); all-fail returns 0 and emits no audit and keeps every key alive; happy path unchanged byte-for-byte (4 writes, cap=2, evicts 2, audits 2); `SystemExit` propagates past the containment (BL-165 invariant preserved). (ADR 0004, ADR 0008, ADR 0020)

- `BL-228` [resolved] [S] `RoutingChainDispatcher.dispatch` iterated its cheap-first chain (`for dispatcher in self._chain: matches = await dispatcher.dispatch(...)`) with no per-link exception containment, so a single raising link (a network `LLMDispatcher` raising `DispatchError` / timing out, an embedding provider blip) crashed the whole chain and discarded the best-effort fallback the chain documents, including the matches already gathered from the cheaper links that ran first. If an object is deleted between the LIST and the HEAD (S3's documented concurrent-access / eventual-consistency window: another writer, a concurrent `read` lazy-expiry delete, or a concurrent `sweep_expired` run), HeadObject returns HTTP 404 (`NoSuchKey`, confirmed against the S3 HeadObject API documentation) and the raw call crashed the whole sweep / eviction scan, leaving every later expired or over-capacity object unprocessed. `S3Store._get_live` already treats this not-found case as "absent" and propagates every other `ClientError`, but the two metadata-scan loops bypassed it. Only the HEAD needs the guard: S3 DeleteObject is idempotent so the sweep DELETE cannot raise on an absent object, and the evict DELETE fan-out already has BL-227 containment. Deliberately narrow: a non-not-found `ClientError` (throttle, `AccessDenied`, outage) still propagates, so the "should the parent sweep be best-effort for transient errors too?" question stays open rather than being silently answered. 9 new tests (`tests/memory/test_bl229_s3_head_toctou.py`): `_head_metadata` returns metadata for a present object / `None` on 404 / `None` on typed `NoSuchKey` / propagates a non-404 `ClientError`; `sweep_expired` skips a concurrently-deleted object and still sweeps the valid expired one, propagates a non-404 HEAD error, and is unchanged on the happy path; `evict_to_capacity` skips a concurrently-deleted object and proceeds over the rest, and propagates a non-404 HEAD error. (ADR 0004, ADR 0008, ADR 0020, ADR 0021)
- `BL-230` [resolved] [XS] Deliberate non-finding (documented, not a code change): the four `float(exp) if exp is not None else None` sites in `memory/dynamodb.py` (`_live_item`, `_list_sync`, `_scan_sync`, the `compare_and_set` match branch) are the same bare-`float` shape BL-226 replaced with `_safe_float` in `memory/s3.py`, but the DynamoDB `N` data type is server-validated to a documented finite range (positive `1E-130` to `~9.9E+125`; "exceeding this results in an exception"), so NaN / +inf / -inf / unparseable cannot be stored in an `N` attribute through its API, and `item.get("exp", {}).get("N")` already yields `None` for a wrong-type (String) attribute. - When merged, change to `[resolved]` and add the merge commit.
- New L2 items discovered after Phase 5 are added with the next free ID per section and dated.
- L3 items use the `BL-1xx` range, are sourced from ADR 0007 revisit triggers and in-code deferrals, and are dated when added. The same start/merge status transitions apply.
