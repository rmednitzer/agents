## Conventions

Each item has an ID, status, size estimate, source ADR, and notes.

- Status: `pending`, `in-progress`, `blocked`, `resolved`.
- Size: `XS` (~30 min), `S` (~1 to 2 h), `M` (~half day), `L` (~day or more).
- IDs are stable; do not renumber on removal. Use `resolved` instead of deleting.

## Security hardening (Tier 0)

First increment delivered 2026-05-17 (ADR 0008). The gate is defence in
depth, not a sandbox (`LIMITATIONS.md` L3).

- `BL-112` [resolved] [M] Marketplace `SkillSource` and integrity verification on install. Delivered (ADR 0008): bounded download / member / size caps and optional `sha256`. Delivered (ADR 0010): the hardened download/extract factored into one audited path, a `SignatureVerifier` hook (`signature` / `verify_signature`, framework binds no crypto vendor), and a generic `MarketplaceSkillSource` (configurable URL template, `strip_components`) over the same hardened path. Extends `BL-054`. (ADR 0006, ADR 0008, ADR 0010)
- `BL-133` [resolved] [M] Skill execution isolation. Delivered (ADR 0008): `discover_skill(allow_contract=...)` and an `install_skill` default of `allow_contract=False` so an untrusted bundle's `contract.py` is not executed. Delivered (ADR 0016): the `skills.execution.SkillContractExecutor` Protocol with two in-tree references: `InProcessSkillContractExecutor` (default, backward-compatible, the L1 behaviour) and `SubprocessSkillContractExecutor` (load + every predicate evaluation in a long-lived Python subprocess; `resource.setrlimit` bounds CPU time, address space, and open files on POSIX; IPC framing is length-prefixed, parent->child pickle, child->parent JSON so a malicious bundle cannot RCE the parent). `Skill.contract()`, `discover_skill(executor=...)`, and `install_skill(executor=...)` forward the executor; defaults preserve every existing call site's behaviour. Capability isolation (filesystem / network / syscall) stays the out-of-tree extension point by ADR 0001 (the same pattern as `KeyProvider` / `Embedder` / `SkillSource`). 12 new tests cover Protocol satisfaction, in-process / subprocess load + evaluate, missing-export / malformed-import / predicate-raise / child-crash boundaries, and loader-level forwarding. ## EncryptedStore multi-key legacy migration (2026-05-23)

A capability consolidation, not an audit fix. Runbook 7.4 candidate 4: the BL-181 authenticated legacy fallback was current-key only (L16); BL-196 adds an opt-in multi-key fallback over a new optional `IterableKeyProvider` Protocol, lifting the L16 restriction without breaking the default. Same conventions and ID discipline; `BL-1xx` range.

- `BL-196` [resolved] [S] `BL-181` shipped an authenticated legacy fallback under the current key only, so adopting a `VersionedKeyProvider` on a store sealed by a plain `KeyProvider` could only read values whose plaintext key matched the current ring version; legacy data under a rotated-away key required a re-encryption pass through the old store first (the `LIMITATIONS.md` L16 contract). Additive: every existing call site is unchanged. (ADR 0007, ADR 0011, runbook 7.4 #4)

## Twelfth code audit (ADR 0022, 2026-06-01)

A twelfth in-depth audit, by area, against the same green gates. It
re-walked the non-finite-numeric class (`NaN` / `+inf` subverts a
numeric control because every ordered comparison with `NaN` is False
and `+inf <= 0` is also False) against the numeric *configuration*
boundaries the prior NaN audits (all on value / data boundaries) had
not reached, the peers of the `Namespace.retention_seconds` boundary
BL-197 hardened. Two findings, split by sub-mechanism; the clear bugs
were fixed additively with regression tests in the same increment.

range.

- `BL-231` [resolved] [S] Numeric-configuration *specs* with no finiteness / sign validation: `ActionBudget` (`harness/budgets.py`) and `RetryPolicy` (`harness/runtime.py`). `ActionBudget(max_cost_usd=float("nan"))` constructed cleanly and the tracker's `consumed > float("nan")` check was always False, so the cost ceiling the operator declared was silently disabled for the whole run; the same held for `max_wall_clock_seconds`, the `max_wall_clock_seconds_per_tool` values, and `+inf` on any of them, with negative limits accepted as a meaningless spec. This is the exact dual of `BL-221`, which hardened the *consumed* side of `consumed > limit` (the caller-fed floats into `BudgetTracker`) but left the *limit* side open. `RetryPolicy` had the same gap: a `NaN` `backoff_base_seconds` / `backoff_max_seconds` makes `delay_for` non-finite, and `asyncio.sleep(NaN)` returns immediately (`min(NaN, deadline)` keeps the `NaN`), turning the bounded exponential backoff of `BL-136` into a no-delay retry storm against the failing provider; a negative `max_retries` or a `circuit_breaker_threshold < 1` is likewise meaningless. Delivered: an `ActionBudget` `model_validator(mode="after")` (two module helpers `_validate_float_limit` / `_validate_int_limit`) rejecting `NaN` / `+inf` / `-inf` / negative on every scalar limit and per-tool map value, and a `RetryPolicy.__post_init__` validating `max_retries >= 0`, finite-non-negative backoff, and `circuit_breaker_threshold` None-or-`>= 1`. `None` (unlimited) and `0` (a zero ceiling, e.g. `max_cost_usd=0.0`) stay valid, so every existing spec is unaffected; validation is at construction (ADR 0007 load-time stance, matching `Namespace.resolve_ttl` BL-197 and the `MultiDispatcher` weight guard BL-205). (ADR 0003, ADR 0011, ADR 0018, ADR 0022)
- `BL-232` [resolved] [S] Positivity guards a non-finite value bypasses: `MCPServerSpec.timeout_seconds` (`harness/mcp.py`) and `TTLSweeper.interval_seconds` (`memory/sweep.py`). Both rejected non-positive values with `value <= 0`, but `NaN <= 0` and `+inf <= 0` are both False, so a non-finite value passed a guard whose docstring claims "must be positive". `MCPServerSpec(timeout_seconds=float("nan"))` was accepted; more acutely, `TTLSweeper(interval_seconds=float("nan"))` was accepted and the loop's `asyncio.wait_for(self._stop.wait(), timeout=NaN)` raises `TimeoutError` immediately, turning the maintenance loop into a no-delay busy-sweep that hammers the backend's `sweep_expired` (Redis / DynamoDB / S3 network I/O) as fast as the event loop allows. ## Code audit (ADR 0023, 2026-06-06)

A thirteenth in-depth audit, by area, against the same green gates. It
re-walked the fan-out per-member failure containment class (`BL-222`
`MultiDispatcher`, `BL-223` `MultiSink`, `BL-227`
`BoundedS3Store.evict_to_capacity`, `BL-228` `RoutingChainDispatcher`)
against the one sibling surface no prior audit had reached: the

- `BL-233` [resolved] [S] `S3Store._sweep_sync` (`memory/s3.py`) and `DynamoDBStore._sweep_sync` (`memory/dynamodb.py`) issued a per-item network DELETE (`delete_object` / `delete_item`) inside a Python loop with no exception containment, so a single transient backend error (S3 `SlowDown` / throttle, DynamoDB `ProvisionedThroughputExceeded`, a network blip) on one expired item propagated out of the loop and aborted the entire sweep pass: every later expired item in the same listing / scan was left un-swept for the cycle, and the count of items already deleted in this pass was discarded (the function raised instead of returning). The failed item stays alive and the next `TTLSweeper` interval retries it (the `BL-199` resilience contract, extended one level down). Scope: the two network adapters with the per-item-loop shape (the other adapters' sweeps are bulk, single-statement, or single-`zrem`); `DynamoDBStore`'s eviction stays all-or-nothing via `_batch_write`-with-retry (a bounded cap-meeting operation differs from unbounded periodic sweep), so S3 is internally consistent (per-item best-effort sweep + evict) while DynamoDB's sweep is best-effort and its evict batched, each the right shape for the operation. 8 new regression tests (`tests/memory/test_bl233_sweep_delete_containment.py`, 4 per adapter via the BL-226 / BL-227 `moto` + flaky-client pattern: partial failure, total failure, happy-path-unchanged, BaseException-propagates). (ADR 0004, ADR 0019, ADR 0020, ADR 0021, ADR 0023)

## Compaction, summarisation, tiering (ADR 0024, 2026-06-09)

The long-horizon context-engineering half of `BL-135` (S2), split into
two items per the established one-capability-per-ID discipline and
delivered together. Both are drivers / compositions over the existing
store Protocols (the `TTLSweeper` / `BL-131` precedents): no adapter

- `BL-234` [resolved] [M] Memory compaction and summarisation: fold N source entries into one summary entry and delete the sources, so a long-horizon workload's keyspace stops growing unbounded (lazy expiry `BL-195`, the sweeper `BL-080`, and the size bounds `BL-212`-`BL-225` reclaim by dropping; compaction reclaims by condensing). Delivered: `memory.compaction` with (a) the `Summarizer` Protocol, memory-local and minimal (bytes-in/bytes-out) so the framework binds no vendor (ADR 0001; an LLM-backed summarizer satisfies it out of tree, the `BL-110` / `BL-131` stance); (b) `TruncatingSummarizer`, the deterministic dependency-free reference: head-plus-tail byte-budget truncation around an elision marker, exact `max_bytes` output on over-budget input, load-time `ValueError` when the marker leaves no content budget (ADR 0007); (c) `MemoryCompactor`, a driver bound to one store and one summarizer. Atomic mode (default) requires `VersionedMemoryStore` + `TransactionalMemoryStore` at construction (load-time `TypeError`) and commits the summary write plus all source deletes in one version-gated `transact`: a source rewritten / expired / deleted between read and commit fails the whole transaction and `compact` returns `None` (the `BL-072` give-up convention; no lost update, no partial application). `atomic=False` is the explicit opt-in for transaction-less backends (S3): write-summary-then-delete-sources with per-source delete-failure containment (the `BL-233` idempotent-DELETE convention), a partial-failure recovery that is lossless only for rolling compaction (a non-rolling re-compact rebuilds the summary from survivors alone), and the documented single-writer-per-key lost-update window (`BL-224`/`BL-225` posture). Rolling compaction is supported: `target_key` may appear in `keys`, the previous summary folds into the new one, version-gated but excluded from the deletes. On DynamoDB the 100-item `TransactWriteItems` cap bounds one call at 99 live sources plus the summary write. Audit events come for free through the store's own ops (`BL-040`). 30 test cases (`tests/memory/test_bl234_compaction.py`): Protocol satisfaction, truncation arithmetic including the `joined[-0:]` zero-tail guard, atomic commit / conflict / rolling / TTL / audit paths on `InMemoryStore` + `SQLiteStore`, best-effort paths, and the construction-time rejections. (ADR 0001, ADR 0004, ADR 0007, ADR 0011, ADR 0014, ADR 0024)
- `BL-235` [resolved] [M] Hot/cold memory tiering: keep the working set in a fast, often size-capped, short-retention hot tier and the long tail in a durable cheap cold tier, behind the plain `MemoryStore` surface. Delivered: `memory.tiering.TieredMemoryStore`, a composition of two namespace-matched stores (`name` and `workload` must agree, checked at construction with a load-time `ValueError`, ADR 0007; `retention_seconds` may differ per tier, short-hot / long-cold being the point). Reads fall through hot to cold and promote by default; promotion uses `compare_and_set(key, None, value)` when the hot tier implements `CASMemoryStore` so a concurrent hot write is never clobbered by the older cold value, degrading to a plain write on CAS-less tiers under the single-writer posture. Writes land hot-first then invalidate the cold copy (`invalidate_cold_on_write=False` opts out per write and accepts the documented resurfacing window); deletes go cold-first so a fall-through read can never resurrect deleted data. `demote(keys)` copies live hot values down then deletes the hot copy, version-gated on a `VersionedMemoryStore` hot tier (a concurrently rewritten or deleted key stays as-is, is not counted, and the just-written cold copy is removed again so a lost race leaves no stale ghost); the wrapper validates keys on its own L1 surface (the `ACLStore` precedent); `demote_to_capacity(max_hot_keys)` is the `evict_to_capacity` shape (`BL-212`) with demotion instead of loss, ranked by the wrapper's first-write sequence (an overwrite keeps its slot, the `BL-212` insertion-order semantics; LRU stays out of tree, `LIMITATIONS.md` L5) with unknown keys carrying the `BL-224`/`BL-225` legacy sentinel 0, oldest-first, ties lexicographic. Extension Protocols of the inner tiers are deliberately not forwarded (a transaction spanning two tiers has no single-store semantics; ADR 0004 "don't fake it"). 36 test cases (`tests/memory/test_bl235_tiering.py`): fall-through / promotion / CAS race / invalidation / delete ordering, versioned and plain demotion including the raced-rewrite case, capacity ranking with legacy and promoted keys, per-tier TTL behaviour, and the construction-time rejections. (ADR 0001, ADR 0004, ADR 0007, ADR 0014, ADR 0024)
